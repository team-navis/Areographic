# 근거 사례 한 건: 자료 → 계획 → 사람의 판단 → 후속 과제

`trace-sample.json`은 PAD의 `현장 대조 · 기록 · 경보` → `② 현장 기록` → `임무 기록 내보내기`가 만든 파일이다. 한 번의 모의 임무에서 무엇이 무엇으로 이어졌는지 식별자로 따라갈 수 있게 묶었다. 판단이 나아졌다는 주장은 하지 않는다. 이어져 있다는 것만 보인다.

## 이 표본을 만든 방법

`MW_URL=http://127.0.0.1:4180/ node tools/evidence-trace.mjs` (프로덕션 빌드, 헤드리스 Chrome).

- 모의 대원 시연 응답은 꺼 두었다(`holdAuto`). 모든 확인·대조·응답·선택·개시는 HUD 버튼 1 또는 HUD 대체 입력 명령으로 넣었다. 그래서 기록의 `actor`가 전부 `human`이고 `scriptedCrewLog`가 비어 있다.
- 사람이 직접 한 것이 아니라 스크립트가 사람 조작 경로(버튼, 입력 명령)를 눌렀다. 실제 참가자의 판단 기록이 아니다. 응답 내용은 스크립트에 적어 둔 예시다.
- 경로 이동은 검사용 훅(`debugSetS`)으로 건너뛰었다. 그래서 임무 시계가 수십 초다. 기지 지시와 우주기상 경보는 PAD 버튼이 부르는 함수를 직접 불렀다.

## 파일에서 따라가는 순서

1. `inputs`: 입력 자료의 식별자와 출처, 이 저장소에 적힌 해시. HiRISE DTM·정사영상, CTX DTM, M20 주행선·정지점, 전방 Hazcam 메시 산출물, Navcam 메시, PIA26368, PIA26640. 해시는 로컬 파일 기준이며 원본을 다시 받아 대조한 것은 아니다. 메시의 높이 이동·가장자리 변형·착색은 연출이라고 적혀 있다.
2. `plan`: 계획 버전, 결정자, 이동 가정(도보 1.4 m/s 또는 로버 3.5 m/s, 둘 다 모의), 작업 목록, 계산된 돌아설 시각. 경로 길이와 경사는 주행선과 DTM에서 계산한 값이다.
3. `package`: 대조 패키지 회차, 어느 계획 버전용인지, 원본 영상 ID, 선 묶음 지문(`lineFingerprint`), 채취 예정 지점.
4. `transmissions`: 계획·패키지·기지 지시·경보 각각의 전송 / 수신 / 확인 / 선택 / 실행 시각과 누가 했는지.
5. `responses`: 현장 대조 결과(어느 패키지에 대한 것인지 포함), 관찰 항목별 응답(`판단 불가` 포함), 메모, 복귀 개시, 임무 종료.
6. `records`: 현장에서 만든 기록과 기지가 받은 시각(`receivedAtPad`).
7. `followUps`: 받은 기록에서 나온 후속 확인 과제와 원래 기록 번호(`fromRecordId`), 다음 탐사로 넘기기로 표시했는지.

## 이 표본에서 이어지는 한 줄

Hazcam 메시 영상(`FLF_1215…`)에서 뽑은 선 → 계획 v2용 패키지 r1 → 대원이 현장에서 일치 확인(기록 1) → PIA26368·PIA26640을 보며 `반점: 판단 불가`(기록 3) → 메모(기록 6) → 기지 수신 → 후속 확인 과제 `반점: 판단 불가 · 추가 확인 필요`.

같은 실행에서 확인한 것: 기지 복귀 지시를 확인한 뒤 `보류`하면 움직이지 않고(`remoteReturn.declined`, `executedAt: null`), 우주기상 경보에서 `복귀 선택` 뒤 `복귀 개시`를 눌러야 `executedAt`이 찍힌다.

## 한계

- 시각·위치·산소·선량·교신은 모의 값이다. 응답은 육안 기록이며 분석·판정이 아니다.
- PIA26640과 PIA26368의 위치 정합은 확인하지 않았다.
- 화면 캡처(`hasCapture`)는 모의 화면이며 파일에 넣지 않았다.
- 저장은 브라우저 세션 안에서만 유지된다. 내보낸 파일이 유일한 보관본이다.
